# Implementation（对应论文 §6）

我们独立实现了 SpecAuditor 的一个原型，由约 3600 行 Python 代码组成
（核心模块 `sa/` 1910 行 + 实验脚本 `scripts/` 1651 行）。接下来，我们
介绍其关键的实现细节。

## 大语言模型查询

对于所有涉及大语言模型查询的任务，我们通过在线 API 访问模型
（DeepSeek-V4-Flash-0731，OpenAI 兼容端点）。每个请求都包含明确的格式
指令，要求模型以 JSON 格式返回结果以便进行结构化解析；客户端内置容错
解析（提取第一个 JSON 对象）、超时（120 秒）与重试（最多 5 次）机制，
并统计每次运行的 token 消耗。

## 规范提取

我们使用 git 命令行（`git log` / `git diff`）解析每个补丁并提取其描述，
同时去除诸如作者和审阅者信息等元数据（clean message）。对于补丁代码，
我们使用命令 `git diff -W` 检索修改函数的完整源代码，该命令以带有完整
函数上下文的 diff 格式表示补丁；随后用 tree-sitter 从 diff 中提取补丁
前后的对应函数体。在规范验证期间，我们解析补丁前和补丁后版本的函数，
将两者与提取的规范一并提交给 LLM 做差异验证（pre 违反 / post 满足）。

## 规范生成

在规范生成过程中，我们从官方 Linux 内核文档构建检索语料库（14709 个
实体-描述对）。我们使用 BAAI/bge-large-en-v1.5 嵌入模型对描述进行编码，
并将向量存储在我们自实现的 numpy 向量库中（`sa/vector_store.py`）以进行
高效的相似性搜索。我们计算归一化嵌入上的 L2 距离（与论文一致，
score = 1 - distance），使用 top-k（k=100）检索并按相似度阈值（0.15，
本地嵌入分布调优确定）过滤。检索到的候选实体提交 LLM 判定约束适用性，
通过则实例化为新的生成规范。

## 基于抽象语法树的代码检索

为了在规范生成和漏洞检测中进行代码检索，我们用 tree-sitter 自建了
代码索引（`sa/code_index.py`），覆盖 59.8 万函数、43.9 万结构体与
440 万调用点，存储于 SQLite。论文使用 Weggli（同样是基于 tree-sitter
构建的 AST 语义代码搜索工具）并声明"不依赖于任何特定语言，其他 AST
搜索工具可类似替换"——我们的 tree-sitter 索引正是论文所允许的等价
替代。为自动化上下文提取，我们设计参数化的查询模板（函数定义、
结构体定义、调用点），运行时用目标实体实例化并查询收集相关代码片段。

## 漏洞检测与报告修剪

在漏洞检测中，我们先用 AST 查询定位每个规范实体相关的候选函数，再
将规范与候选函数代码提交 LLM 做违规检查。违规报告进入修剪阶段：LLM
可请求最多 5 次按需上下文（实体定义/使用情况），迭代确认或驳回报告。
为提高吞吐，检测与修剪阶段采用 4-8 线程并发，并用 done 集合实现断点
续跑（状态持久化到 `stage3_state.json`）。
